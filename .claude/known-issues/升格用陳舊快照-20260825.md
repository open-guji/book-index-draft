# `promote` 用陳舊快照——升上去的是舊本，而無任何校驗會報

2026-08-25 遼金元輪實見。**此病比撞號隱蔽得多**：撞號至少有 E07 可驗，
而這一型 E01／E02／E03／E04 **全都對得上**——各自墓碑指得對、production 檔也在、
引用也不裸——**它們只驗「指向」，不驗「內容是否新」**。

## 一、怎麼發生的

並行會話於 `2a4d0f5b14`「五代十國與遼金元 4,421 條升格」把遼金元整批升格。
`promote_item` 之流程是：

1. Phase 1 讀 `draft_metadata`
2. …鑄 id、寫 production 檔（**內容取自第 1 步所讀**）
3. Phase 2 回寫 draft 墓碑（**內容亦取自第 1 步所讀**，加 `_promoted_to`）

四千餘條之批次要跑很久；而**該會話之 git 工作區落後於 main**——本會話同日
所推之遼金元 L1–L7（正題、正撰人、歸一斷代、補 desc、判 loss_status）
不在其工作區內。於是：

- 其 production 檔寫的是**改正之前**的內容
- 其 draft 墓碑也回寫成**改正之前**的內容——**把已推上 main 的改正抹掉**

## 二、更壞的一步：git 之行級自動合併默默取了舊值

合流時，只有 11 檔報 `UU`／`DU`；其餘**行級自動合併「成功」**，
而合出來的是**對方之舊值**。實測：本會話所改之 795 檔中 **211 檔之知識欄被回退**
（`indexed_by` 124、`authors` 83、`title` 1、`related_works` 2……），
其中 **101 檔已升格**——即 production 側也是舊本。

例：《紹興甲寅通和錄》之王繪由「宋」退回「金」；
《讀易考原》之 `indexed_by` 丟了併入之《經義考》一節。

## 五、戒

1. **長批次 promote 之前必先 `git pull --no-rebase`**，且**升格與改資料不可同時跑**。
   本輪之亂全由此起。
2. **合流之後不可信 git 之「自動合併成功」**。JSON 之行級合併可以合出
   語法有效而語義錯誤之結果（SKILL 坑 28 已記其一型：合出衝突標記；
   此處是另一型：**默默取了對方之舊值而毫無痕跡**）。
   合流之後當**逐檔比對本會話所改之欄**，不能只看 `git status` 之衝突數。
3. **校驗之缺**：`validate-promotions` 之 E01–E04 只驗指向不驗內容。
   宜補一驗——**production 條與其 draft 墓碑之知識欄應一致**
   （墓碑是升格當時之凍結快照，二者本該逐字相同；不同即是一方被改過而另一方未跟）。
   此驗若早有，本輪之 101 條與九組重出當場即現。**屬 manager 車道，未動。**
