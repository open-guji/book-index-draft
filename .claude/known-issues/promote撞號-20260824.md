# `book-index promote` 之 production id 撞號（2026-08-24 實見兩例）

## 現象

`book_index_manager promote` 為升格條生新 production id 時，**會生出與既有
production 條目相同之 id**；CLI 只印一行警告而不阻止，其檔遂被**覆寫**：

```
[WARNING] [book-index] Renaming file for d59f2870u874: d59f2870u874-宋書.json
          -> d59f2870u874-文選.json (title changed)
```

於是 `promotions.json` 中兩個 draft 指向同一 production id，
而 production 只剩後升者之內容——**先升者之 production 條目連內容帶題名一併丟失**。

## 兩例（皆 2026-08-24，皆已修）

| production id | 撞者 | 留 | 撤銷重升 |
|---|---|---|---|
| `d59f2870u874` | 宋書 `1ev3c1fplga2o` ／ 文選 `1evcmocs9vtog` | 文選（後升，內容在） | 宋書 → `d59f287ki6f4` |
| `d59f24m10qv4` | `1evftxcnoxyio` ／ 九旗飛變 `1evftxd01fw1s` | 九旗飛變 | `1evftxcnoxyio` → `d59f287ki6f5` |

第二例是別的會話 14:48 之升格所生，非本輪；本輪順手同法修之。

## 何以會撞

二例皆是**同一批 promote 之內連續生 id**（同一秒、同一進程）。
Snowflake 之 sequence 若未跨毫秒遞增（或每次 gen-id 重取時戳而 sequence 歸零），
同毫秒之二次調用即得同號。**升格之批越大越易撞**——
本輪 1,652 條一次升，撞一組。

## 動手前該做的

1. **升格後必查**：`promotions.json` 之 `production_id` 反查是否一對多。
   一行即可：
   ```python
   pr=json.load(open('promotions.json'))['promotions']; rev={}
   for k,v in pr.items(): rev.setdefault(v['production_id'],[]).append(k)
   print({k:v for k,v in rev.items() if len(v)>1})
   ```
2. **修法**：以 production 檔之 `title` 認出「留哪一條」，
   另一條去其 draft 之 `_promoted_to` 與 `promotions.json` 之目，再 promote 一次。
   draft 側之內容不因升格而刪，故可全復。
3. **根治**須改 `book_index_manager` 之 gen-id（sequence 跨調用遞增，
   或 promote 生 id 後先驗 production 無此檔方寫）——屬 manager 車道。

## 已修（2026-08-24 晚）：兩支根因，兩處修法

撞號有**兩支**，都在 `book-index-manager`，都已修並有迴歸測試：

| 支 | 何以撞 | 修於 | commit |
|---|---|---|---|
| **進程內** | `next_id` 以單一 `last_status` 判其是否同一時間單位，兩個 status 交替生成時每次切換都把 `sequence` 打回 0 而 timestamp 未推進 | `id_generator.py` 改為**每個 status 各記一份 `(last_timestamp, sequence)`** | `ef22223`（隋唐輪次，另一會話） |
| **跨進程** | 生成器之 `(last_timestamp, sequence)` 是**進程內**狀態，而 official id 之時戳單位是**秒**——同一秒內兩次 CLI 調用各自從 `sequence=0` 起 | `promotion.py` 新 `_mint_unique_official_id()`：**鑄號處查重重試**（查 promotions.json 已錄之 production_id ＋ 兩倉實檔），不問撞號之由一概擋下 | `5b082b9`（南北朝輪次） |

**並補 `validate-promotions` 之 [E07]**：同一 production_id 被兩條以上 draft 佔用。
此型之難見正在 **E01/E02/E03 全都對得上**（各自墓碑指得對、production 檔也在），
非專驗不能見——`ef22223` 之訊息已指出這是三個「漏而不覺」之由的第三個，而其驗當時仍缺。

**故本檔第一節所記之「升格後必查」，現已由 `validate-promotions` 自動辦。**
惟仍宜於每輪升格之後跑一次（它同時驗 E01–E06），且**用新版 CLI**——
舊版無 E07，跑了也看不見。

**已知歷史撞號皆已復原**：隋唐九組、漢代一組（《風角注》被《九旗飛變》覆蓋，
三個月無人知）、南北朝一組（《宋書》被《文選》覆蓋）。
現況 `promotions.json` 11,102 目，一對多 **0**。
