# draft → production 升格：並行方案（2026-08-21 擬）

秦以後各代的升格要並行推進。本檔定三件事：**什麼時候可以開始、按什麼軸分工、
撞車了怎麼辦**。所有數字都是 2026-08-21 於 `22533120c6` 實測，非估算。

## 零、結論先行

1. **現在還不能開始。** 有一個硬閘：`book-index-manager` CLI 的六個缺陷已修在
   `claude/fix-index-period-and-indent` 分支而**未發版**。未發版之前，任一會話跑一次
   `reindex` 就製造四十四萬行 index diff——**並行會話之間必然互相衝突且無法合併**。
   這不是「小心點就好」的事，是先決條件。詳見〈二〉。
2. **不要按朝代分整備工作。** 實測：45% 的 Work 沒有 `period`，54% 的同名組跨代，
   252／332 個主要整理本檔跨三代以上。按朝代切，切不開。詳見〈三〉。
3. **分兩段：整備按志書切，升格按朝代切。** 整備階段（合併、拆磁鐵、救落空、補
   period）動的是跨代的東西，按**志書**分工檔案面才不重疊；整備完成後記錄穩定，
   升格階段才按朝代切。詳見〈四〉。
4. **一條記錄升格即成墓碑，此後改不了。** 這是排程的第一約束——任何全庫統一處理
   必須在該條升格之前做完。詳見〈一〉。

## 一、先弄清楚升格到底做了什麼

實測 171 條已升格記錄：

- **157 條是墓碑**——草稿檔被削成 `{id, type, title, _promoted_to, _promoted_at}` 五個欄，
  其餘全部移往 production。例：`Work/1/e/v/1ev3bb72dbqio-荀子.json` 現在只剩五行。
- 14 條是舊式（2026-05 那批），保留全文另加 `_promoted_to`。

**推論一（排程約束）**：升格之後那條記錄**不能再curate**。所以
「同名合併」「拆磁鐵」「補撰人」這類全庫統一處理，**必須在該條升格之前做完**，
一條都不能漏。漏了就只能到 production 去改，那是另一個倉、另一套流程。

**推論二（分組約束）**：同名組必須**整組同時定案**。組內任一條未定案，全組不得升格
——否則會出現「明代那條該併入宋代那條，可宋代那條已經是墓碑」的死局。
實測跨代同名組 **995 組**，另有 1,233 組是「有 period 的與無 period 的混在一起」，
合計 **2,228／4,090 組（54%）跨越朝代邊界**。

## 二、硬閘：CLI 未發版之前不要動

`.claude/known-issues/先秦promote待決.md` §六 記了六個缺陷。就並行而言，**致命的是第三條**：

> shard 寫入固定 `indent=2`、不排序、無條件補尾換行 → 改一條產生四十四萬行 diff

倉庫既有格式是 `indent=1` 且按 id 排序。只要有一個會話跑了舊 CLI 的 reindex，
它那條分支的 16 個 index shard 就整個重排；其他會話的分支再合併過來，**每一個
shard 都是全檔衝突**。`scripts/preqin-fix/normalize_index.py` 就是為此而寫的補救，
但補救是事後的，並行時來不及。

其餘五條也都要，尤其：
- `build_index_entry` 不輸出 `period`／`loss_status`／`work_id`／`promoted_to`
  → 一次 reindex 抹掉全庫 40,738 條 period。並行時等於一個會話毀掉所有人的成果。
- 條目派生欄已改帶 `_` 前綴而代碼仍讀舊名 → **已升格記錄的寫保護全部失效**，
  草稿副本可逕改而不被攔。並行時這會讓「已升格不得再改」的約束形同虛設。

**建議**：開一個會話專責推 CLI 發版，其餘會話在此之前只做**不碰 index 生成**的整備
（改 Work 檔與 collated section，index 用倉內既有的手工同步法，見〈六〉護欄）。

## 三、為什麼按朝代切不開（三個實測的漏）

| 漏 | 實測 |
|---|---|
| **一、近半數記錄沒有朝代** | 74,463 條活記錄中 **33,219 條 `period` 為空**（45%）。按朝代分工，這 33,219 條沒有歸屬 |
| **二、同名組跨代** | 4,090 組同名中，跨代 995、與無 period 混合 1,233，**合計 54%**。最常見的代對是 ming↔qing（390 組）、liao-jin-yuan↔ming（116）、ming↔song（73） |
| **三、整理本檔跨代** | 繫連 ≥50 節的整理本檔共 332，其中 **252 個跨三代以上**。國史經籍志集類（3,962 節）、子類上（3,461）、史類（3,837）各跨 **11 代**。兩個朝代會話一定會同時改同一個 `集類.json` |

第三漏其實**可以忍**——JSON 是行導向的，改一行 `"work_id": "..."` git 能自動合併。
真正致命的是**整檔重寫**（`json.dumps` 換了縮排或鍵序），那會把可合併的變成不可合併的。
所以規矩不是「別碰同一個檔」，而是**「碰同一個檔時只做精準字串替換，絕不重排」**。

## 七、會話認領協議

無鎖不行，中央鎖檔本身又是衝突點。用**一會話一檔**的認領目錄，天然無衝突：

```
.claude/parallel/claims/<branch-name>.json
{
  "branch": "curation-song-0821",
  "phase": "A",                       // A=整備  B=升格
  "catalogs": ["1ev3bb403quio"],      // 階段 A：認領的整理本 id
  "periods": [],                      // 階段 B：認領的 period
  "work_ids_exclusive": [],           // 需要獨佔的個別 Work（跨志改動）
  "started_at": "2026-08-21T...",
  "note": "直齋整備"
}
```

**規矩**：
1. 開工前先寫這個檔並推 main，再開始改資料。
2. 開工前掃一遍 `claims/` 目錄，有重疊就先協調，不要硬上。
3. 收工刪掉自己的檔。
4. **跨認領範圍的改動一律不做**——記入 `.claude/parallel/handoff/<branch>.md`，
   交由對應會話或併池會話處理。

**併池會話**（序列化，只此一個）：專責處理跨志書、跨朝代的合併與磁鐵拆分。
其餘會話只提交候選，不自己併。這是唯一必須序列化的工序，因為合併按定義跨分區。

## 九、建議的推進次序

1. **CLI 發版**（阻塞一切）＋ `promotions.json` 排序／分片。
   格式約定已定並全庫施行竣工（見〈十〉），`chk.py` 三項基線皆 0。
   **另：既已統一 indent=2，CLI 那條「shard 寫入固定 indent=2」的缺陷自然消解**
   ——它本來就寫 2，是倉裡 index/works 為 1 才顯得它在破壞。剩下要修的只有
   「不排序」與「不輸出 period 等派生欄」二事。
2. **三項 schema 決策**（偽書 `authenticity`、原典／注本層級、著錄條/版本條/原典條三分）
   ——越晚做，改動面越大，因為宋明清的別集會把這三個問題乘以一萬。

## 十、JSON 書寫格式：普查與第一波施行（2026-08-21）

並行的機械衝突源頭排第一位的不是 promotions.json，是**書寫格式**。普查全庫
116,671 個 JSON 檔（含 `book-index/` 之 49 個空殼），結果：

| 族 | 檔數 | 縮排分布 | 缺檔尾換行 |
|---|---:|---|---:|
| Work（記錄檔） | 74,759 | 2：74,251／**1：508** | 2,746 |
| Book | 23,719 | 2：23,688／**1：31** | **23,652** |
| Entity | 15,585 | 2：15,582／1：3 | 131 |
| Work/*/fragments | 1,233 | **1：1,196**／2：37 | 1,193 |
| Work/*/collated_edition | 1,206 | 2：830／**1：376** | 796 |
| index/works | 16 | **全為 1** | 0 |
| index/books | 16 | 2：15／1：1 | 0 |
| index/entities | 16 | 全為 2 | 0 |
| index/collections.json | 1 | **1** | 0 |
| Collection | 64 | 2：63／1：1 | 63 |
| 庫根 | 7 | 全為 2 | 4 |

**只有兩個軸不一致**：縮排與檔尾換行。`ensure_ascii`（無一檔把 CJK 寫成 `\uXXXX`）、
分隔符（116,622 檔一律 `": "`）、CRLF、BOM——**皆已一致，逕行寫入約定即可**。

**約定取 indent=2**（見 `SCHEMA.md`〈JSON 書寫格式〉）。理由不是 2 比 1 好，是
**一致才重要**；取 2 是因為記錄檔 99% 已是 2，且 CLI 亦寫 2。少數派共 2,133 檔。

**第一波已施行 1,689 檔**（fragments 1,196、collated_edition 376、Work 94、
Book 19、Entity 3、Collection 1），552,414 行進出相抵，逐檔以
`json.loads(新) == json.loads(舊)` 驗語義不變，**0 檔有變**。

**第二波已於同日合入 `claude/promote-pre-qin-books` 後補完**（59,621 檔）：

| 項 | 第一波後 | 合併該分支後 | 掃平後 |
|---|---:|---:|---:|
| 縮排非 2 | 444 | **18**（該分支重寫 Work／Book 時順帶寫成 2） | **0** |
| 缺檔尾換行 | 27,142 | **59,603**（該分支之寫入器剝尾換行，＋32,461） | **0** |
| 索引檔鍵未按 id 排序 | 1 | **0**（該分支之 reindex 順帶排好） | **0** |

掃平前先驗過十五個遠端分支對 HEAD 的內容差皆為 0，確認無分支在飛。
`chk.py` 三項基線皆改為 **0**——此後不為零即表示有工具用了別的格式，逕跑
`scripts/normalize_json_format.py --apply` 即可。

一句話記為戒：**格式歸一化必須挑「無分支在飛」的時刻做。** 本輪之數字即為明證——
第一波之後尚餘 27,142 檔缺尾換行，等那個分支合進來就變成 59,603，多出的 32,461 檔
全是它一路寫出來的。若第一波就硬掃，掃的那些會被它悉數推翻。
