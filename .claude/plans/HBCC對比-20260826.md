# 與 HBCC《中國歷代典籍總目》對比：缺在哪裡

> 對象：`open-guji/pku-hbcc-data`（國圖＋北大《中國歷代典籍總目》試用版全庫，
> 2,868,633 條，32 家來源書目）。
> 本檔為 2026-08-26 實測，腳本在 scratchpad，數字皆可復現。

---

## 零、一句話

**兩邊不是同一種東西。** HBCC 是**藏本層的聯合目錄**（96% 是館藏著錄，題名經規範化）；
本庫是**品種層的著錄轉寫**（存志文原貌，帶出處與判據）。所以「缺」有三種，
代價與價值差了兩個數量級：

| 缺的種類 | 量 | 該不該補 |
|---|---:|---|
| **一、整家書目未收** | 18 家 / 280 萬條 | 三家史志類該補（約 1.9 萬條），館藏類另議 |
| **二、已收之目中漏的條目** | 約 **1,800 條** | **該補，且可逐條落地** |
| **三、藏本層（Book）整層薄** | HBCC 276 萬 vs 本庫 2.1 萬 | 是取向之別，非缺陷 |

## 一、HBCC 的結構

### 一之一　三層：navinode 樹 + entry 表，記錄自帶 FRBR 層級

`entry_id` 14 位 ＝ 8 位**來源書目前綴** + 6 位序號，序號即該書目自身的著錄次第。
每條記錄四個欄：

```
entry_id        pedigree  cluster_key      summary
10006016000002  20        10006016000002   易傳周氏 2卷 (西漢)周王孫撰 亦見《漢書 • 藝文志》
```

`pedigree` 是**記錄的級別**，由來源書目決定，不是模版：

| pedigree | 層級 | 全庫 | 對應本庫 |
|---|---|---:|---|
| 20 | 品種（work） | 84,487 | **Work** |
| 30 | 版本（expression） | 21,209 | Work＋edition |
| 50 | 藏本（item） | **2,762,937** | **Book** |

`summary` 是著錄全文，`parse.py` 拆成 書名／卷數／責任者（時代・名稱・方式）／版本／
藏處／半葉行數／每行字數／雙行小字／書口／邊欄／魚尾／裝幀／印刷類型／亦見書目／所屬叢書。
未解析詞元 22 / 286.8 萬（0.001%）。

### 一之二　與本庫 schema 的對應

| HBCC | 本庫 |
|---|---|
| `summary` 全文 | `indexed_by[].summary` |
| 書名 | `Work.title`／`indexed_by[].title_info` |
| 責任者（時代・名稱・方式） | `authors[].{dynasty, name, role}` ＋ `entity_id` |
| 亦見《X》 | `indexed_by[].source` |
| `cluster_key` | **本庫無對應**——但本庫的 work 合併＋`related_works` 做的是同一件事，且做得更狠 |
| 所屬叢書 | `Collection` ＋ `contained_in` |
| 藏處 | `Book.current_location` |
| 半葉行數／邊欄／魚尾／裝幀／印刷類型 | **本庫無**（版本形態欄，屬 Book 層） |

**本庫有而 HBCC 全無的**：`period`／`period_basis`（斷代與其判據）、`loss_status`（存佚）、
`fragments`（輯佚檔）、`period_upper`、一切 `*_basis` 判據欄、整理本 `collated_edition`
的節級繫連、Entity 的獨立人物層（24,602 人）。**HBCC 沒有任何判據欄——它只給結論。**

### 一之三　三個要緊的性質

1. **題名經規範化。** 漢志「太史公百三十篇」→ HBCC「史記 130卷 (西漢)司馬遷撰」；
   「孫卿子三十三篇」→「荀子 33卷 (【戰國】趙)荀况撰」；「魯故二十五卷」→「魯詩 28卷」。
   **篇一律折成卷，撰人志所不著者亦補**。本庫反是——存志文原貌，志不著者不補。
   這一條決定了兩邊不能靠題名硬比，下文的比對法即為此設。
2. **`cluster_key` 高精度低召回**，不可當書種數用：全庫 516,294 個聚類中 427,536 個是單條
   （82.8%）；《三輔黃圖》827 條散在 820 個聚類。
3. **導航樹只暴露 12%**，缺口全是不掛節點的叢書子目。該倉是按 entryId 枚舉抓的，非沿樹遍歷。

## 三、缺之二：已收之目中漏的條目（約 1,800 條）

### 三之一　比對法

題名不能直比（見〈一之三·1〉），故：

1. HBCC 側用其 `parse.py` 取出 `書名`。
2. 本庫側**一節取數鑰**：`Work.title`（本庫考定之正題）、`indexed_by[].title_info`
   （著錄原文）、`additional_titles`，另加「撰人前置式」之去撰人形
   （明志、後漢志作「李本固《古易彙編》十七卷」；三國志更把按語一併收入）。
3. 兩側同一套正規化：去書名號與標點（含 `•`）、歸併異體字、剝尾部卷數（「二十四卷」「三篇」）。
4. HBCC 有而本庫該目無者，再分三等：
   - **exact**：其題在本庫別處有（**繫連歸屬之別，非缺**）
   - **near**：本庫有差一字者，或有多／少一二字者（**異體、形訛、題之詳略**）
   - **absent**：本庫全無其影（**真缺候選**）

## 四、缺之三：藏本層（Book）整層薄——這是取向之別

HBCC 2,762,937 條 pedigree 50（藏本），本庫 Book 20,939 條。差 132 倍。

但這**不是缺陷**：HBCC 的藏本層來自五家館藏目錄（叢書綜錄、古籍總目叢書部、古籍善本書目、
國圖善本、北圖普通古籍），記的是「某館藏某書某本，半葉十行、四周雙邊、黑口」。
本庫的 Book 記的是**有數位資源可繫的具體本子**（故宮善本、再造善本、武英殿本、四庫各閣本），
帶 `resources` 與 `_has_image`／`_has_text`。兩者的用途不同。

要不要引入藏本層是個產品決策，不是補漏。若要引，`Book.contained_in` ＋ `Collection`
的架子是現成的（Collection 已全量升格），但 276 萬條會把本庫的體量放大四十倍。

## 五、順帶查出的本庫自身之疵

1. **`indexed_by[].source` 有 4 節誤填 work id**：`d59f2mp38qv4`（3 節）、`d59f2mua7w8y`（1 節）。
2. **明史藝文志的 `title_info` 混有簡體**：如「刘应秋《尚书旨》十卷」「王宾《吴下名贤纪录》一卷」。
   `chk.py` 的「簡轉繁過度轉換」一驗查的是反向，查不出這個。
3. **`title_info` 各志體例不一**，比對時吃了大虧：
   - 隋志作「《晉紀》四卷」（帶書名號）
   - 明志、後漢志作「李本固《古易彙編》十七卷」（**撰人前置**）
   - 三國志作「康 聖賢高士傳贊三卷 康始末具經部易類。」（**按語一併收入**）
   - 補晉志多有 `title_info` 全闕而只有 `summary` 者
   這不算錯——`title_info` 本是著錄原文的節錄，各志原文本不一律——但要作全庫題名檢索
   或跨庫比對，得另立一個規範題欄，或約定 `title_info` 只存題與卷數。

凡取 HBCC 之說，`ai_note` 須寫明「據 HBCC《中國歷代典籍總目》，未覆原書」。
