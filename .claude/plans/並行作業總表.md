## 一、現在可以並行了，但升格還不能

三件事在 8/21 改變了局面：

1. **JSON 書寫格式全庫統一**（indent=2、檔尾一換行、鍵序不重排，`chk.py` 三項基線 0）。
   並行最大的機械衝突源是「某個工具用自己的縮排把整檔重寫」——那會把可自動合併的
   行級改動變成整檔衝突。這條路現在堵死了。
2. **`claude/promote-pre-qin-books` 已合入**，42,254 檔落地。**現無任何分支在飛**
   （十五個遠端分支對 main 的內容差皆為 0）。
3. **`period_upper` 全庫標注**：原本 33,219 條沒有朝代，現在 **31,541 條有了時代上限**，
   既無 `period` 亦無上限者只剩 **1,037 條**。

**但升格仍是單線。** `book-index-manager` 的 `build_index_entry` 仍不輸出
`period` / `loss_status` / `work_id` / `promoted_to`，一次 `reindex` 抹掉全庫四萬條
`period`。升格流程含 reindex，故**在 CLI 發版之前，升格只由一個會話走，且須用手工
同步索引的補救路徑**。（縮排那條缺陷因全庫統一為 2 已自然消解，剩下要修的是
「不排序」與「不輸出派生欄」二事。）

## 二、分工的機制：欄位級所有權

檔案級鎖在這個庫裡行不通——一條 Work 會被十家志著錄，按志分工也躲不開共用的
記錄檔。但 JSON 是行導向的，**一個欄位就是一行或幾行**，所以真正可行的是
**欄位級所有權**：不同車道改同一個檔的不同欄，git 自動合併。

| 欄位 | 誰可以改 |
|---|---|
| `title`、`original_title`、`additional_titles`、`authors` | **併池車道（B）** |
| `related_works`、`books`、合併與刪除 | **併池車道（B）** |
| `indexed_by[]` 中屬於本志的那一個元素 | **該志車道（A）** |
| `collated_edition/**` 之 `work_id`、`section_kind`、節內 `ai_note` | **該志車道（A）** |
| `period`、`period_upper`、`period_basis`、`dynasty` | **斷代車道（C）** |
| `loss_status`、`fragments`、`description` | **對應專項車道（D）** |
| `_` 起首之派生欄 | 誰都別手寫，跑 `chk.py` 以重算值為準 |

**兩個必然衝突的欄，先講好怎麼解**：

- **`ai_note`**——人人都往後面追加，同一行必撞。**規則：衝突一律兩存**，
  把雙方的段落都留下，用空行隔開，按日期排序。不要挑一邊。
- **`updated_at`**——取較晚者即可，不必看內容。

### B 類：同名異書合併（併池，可同時開三條）

4,089 組、10,090 條。**這一類不能按志或按代分**——一次合併按定義把兩家志、
兩個朝代的記錄併在一起。但**可以按「組」分**：一組是原子的，兩個會話認領不相交的
組集合，就永遠不會改到同一條記錄。

分法（任一皆可，認領時寫明）：
- **B1 size≥4**：393 組，信號密度最高，先做。
- **B2 size=3**：622 組。
- **B3 size=2**：3,074 組，量最大而多為同名巧合，優先度最低。

取自己那一份的一行程式（以 B1 為例）：

```bash
python3 - <<'PY'
import json,glob,collections
IW={}
for f in glob.glob('index/works/*.json'): IW.update(json.load(open(f,encoding='utf-8')))
g=collections.defaultdict(list)
for k,v in IW.items():
    if v.get('title') and not v.get('promoted_to'): g[v['title']].append(k)
mine=[(t,ks) for t,ks in g.items() if len(ks)>=4]      # ← 改這一行取你那一份
print(len(mine))
PY
```

**跨代組 1,045、與無 period 混合 1,223——合計 2,268 組（55%）跨越朝代邊界。**
這正是「升格必須等合併做完」的原因：一條記錄升格即成墓碑，組內任一條先升了，
其餘的就併不動。

## 四、全體共通的規矩

1. **索引改哪條同步哪條**（`index/works/*.json` 之 title／path／author／role／
   dynasty／period／original_title／additional_titles 須與記錄檔一致，`chk.py`
   「索引欄位不符」即驗此）。
   **`book-index reindex` 現已可跑**（2026-08-22 解禁——CLI 六項缺陷俱修，
   並在六萬檔實庫上實證：四型無一條增刪錯誤，JSON 三項基線仍為 0）。
   **`index/` 是派生物：兩道撞車不要手工併，重跑 reindex 即正解。**
2. **整理本檔只做精準字串替換**，不整檔 `json.dumps` 重寫。格式既已統一，
   要寫就寫 `indent=2` ＋ 檔尾一換行；**不要再探測縮排**。
3. **只改自己車道所擁有的欄位**（見〈二〉）。越界的事寫進
   `.claude/parallel/handoff/<你的分支>.md`，不自己動手。
4. **`README.md` 與 `SCHEMA.md` 不改**；要記的寫進自己那個 known-issues 檔。
5. **每批之後跑 `.claude/skills/hanzhi-curation/scripts/chk.py`**，對基線；
   有回歸不得提交。
6. **每天至少一次 `git fetch origin main && git merge origin/main`。**
   並行時落後三天的分支基本合不回來——今天合那個 42,254 檔的分支之所以零衝突，
   就是因為它一路在合 main。
7. **`ai_note` 衝突一律兩存**，`updated_at` 取較晚者。
8. **升格是不可逆的**：草稿檔會被削成五個欄的墓碑。凡未定案者不升。

的判準。**
